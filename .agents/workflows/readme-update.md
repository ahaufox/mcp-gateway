description: 自动更新技术型 README.md 的规范工作流，确保文档与代码变更同步。
---

### 背景
为了保证项目文档的实时性和准确性，当代码发生重大逻辑变更、底层架构调整或部署方式改变时，必须同步更新主 `README.md` 文档。本工作流遵循"**变更即文档**"原则——文档不是事后的整理工作，而是变更的一部分。

### 触发条件
当任务涉及以下变更时，**必须**执行此工作流：

| 类别 | 典型场景 |
|------|---------|
| **架构变更** | 新增/删除/替换核心服务（如新增 Redis 缓存层、更换数据库引擎、引入消息队列） |
| **部署调整** | `docker-compose.yml` / `Dockerfile` 结构发生重大变化；新增/重命名关键环境变量（`.env.example`） |
| **关键逻辑** | 后端核心服务（如 `AppService`、Plugin Daemon、聚合网关 `mcp-proxy`）的底层行为发生改变 |
| **子模块变更** | 更新 Git Submodule 引用、新增/删除 `mcp-proxy`、各 `*mcp` 子项目 |
| **API 变更** | 公共端点（HTTP/SSE/WebSocket）的路径、参数、响应结构发生破坏性变更 |
| **集成服务** | `README.md` 中"已集成服务"表格的增删改 |

### 何时**不**触发
- 纯内部重构（无对外行为变化）→ 仅在 `IMPLEMENTATION_PLAN.md` 记录即可
- 单文件 bug 修复、注释调整、依赖小版本升级 → 不需要更新 README
- 性能优化（接口契约未变）→ 在 PR 描述中说明即可

### 执行步骤

#### 1. 评估变更影响
- 回顾本次任务的所有修改（`git status` / `git diff`），判断其是否命中【触发条件】。
- 若未命中 → 在任务总结中显式声明"无需更新 README.md"并说明原因。

#### 2. 定位更新区域
本项目 `README.md` 的实际章节结构（请按需选用，**不要新增未在触发条件中体现的章节**）：

| README 章节 | 适用变更 |
|------------|---------|
| `项目组成` | 子项目增删、技术栈替换 |
| `技术栈` | 核心语言/框架/SDK 升级 |
| `核心特性` | 新增能力（如批量调用、熔断器、钩子链） |
| `快速开始` / `### 本地启动` / `### 远程部署` | 克隆步骤、环境准备、启动命令、部署脚本 |
| `已集成服务` | 新增/移除/迁移服务，更新传输类型或启动方式 |
| `项目结构` | 源码/配置文件位置变动、目录重命名 |
| `环境变量配置` | `.env` 关键变量增删、默认值变更、安全相关变量 |
| `API 端点` | HTTP/SSE/WebSocket 端点路径、参数、响应格式 |
| `🚀 未来规划与社区贡献` | 已交付项从规划迁出；新增规划条目 |
| `详细文档` | 新增/失效的 `docs/*.md` 链接 |

#### 3. 实施更新
使用 `Edit` 工具（精确替换）或 `Write` 工具（重写小文件）更新 `README.md`：

- **语言一致性**：除非用户明确要求英文，否则**默认中文**维护，与现有 `README.md` 风格保持一致。
- **简洁优先**：只描述"用户需要做什么"和"系统表现为什么"，避免琐碎实现细节（细节应留在 `docs/IMPLEMENTATION_PLAN.md`）。
- **Markdown 规范**：标题层级递进、表格对齐、代码块标注语言、相对路径链接使用 `./` 前缀。
- **Emoji 节制**：仅在章节锚点使用（与现有风格一致），不要在正文滥用。
- **重复命令抽离**：若新增了部署/修复/排障命令，**优先**将其固化为独立的 `.agents/workflows/*.md` 文件，再在 `README.md` 中用一行命令引用。
- **变更摘要**：在 `README.md` 顶部或 PR 描述中，列出本次文档变更的要点（新增章节、修改表格项、修复链接等），便于审阅。

#### 4. 验证（不可跳过）
1. **链接校验**：执行 `npx markdown-link-check README.md`（或同等工具）确保所有本地与远程链接可用。
2. **结构渲染**：在 IDE Markdown 预览中肉眼检查一次：表格列宽、代码块语法高亮、锚点跳转（`#` 后章节名）。
3. **行内命令回放**：若更新了启动/部署命令，**至少本地 dry-run 一遍**（不真正启动服务），确认无复制粘贴陷阱（如换行错误的 shell 变量）。
4. **变更审阅**：若团队有 Code Review 流程，README 变更需与代码变更在**同一 PR** 提交并交叉审阅。

#### 5. 提交协调
- README 更新应与代码变更**绑定在同一次提交/PR** 中，不允许独立提交以避免与代码状态脱钩。
- Commit message 建议追加 `docs(readme): <要点>` 前缀（与 `general-git-commit-message.md` 规范保持一致）。

### 反模式（请避免）
- ❌ 复制大段 `docs/IMPLEMENTATION_PLAN.md` 内容到 README
- ❌ 在 README 中记录 TODO、内部决策、未发布特性（应放在 `ROADMAP_CN.md`）
- ❌ 仅修改章节标题但内容已过时
- ❌ 引入未经触发的全新章节（如"插件市场"、"计费说明"）
- ❌ 提交 README 变更后未运行任何验证

### 角色建议
1. 在每次任务完成**前**，主动检查是否需要运行此工作流，而不是等待用户提醒。
2. 维护文档时，始终将自己视为"**首席布道师 (CTO/Chief Evangelist)**"——文字需兼具准确性、亲和力与可操作性，让新读者 5 分钟内完成首次部署。
3. 对存在分歧的描述（如端口号、命令参数），以**代码与配置文件的实际值**为准，不臆测。
