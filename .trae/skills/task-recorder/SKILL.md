# 待办事项记录技能 (task-recorder)

## 何时使用

- 用户在对话中提出了一个需要后续跟进的问题或需求
- 经过调研和分析后，需要对问题和结论进行归档
- 用户明确要求"记录待办"、"归档这个问题"、"整理成待办"
- 对话中发现了值得记录的技术决策、架构隐患或待优化点

## 核心定位

该技能是知识沉淀工具，将对话中的隐性知识显性化，生成可直接用于项目管理的待办文档。不替代 TodoWrite 等实时任务跟踪工具，而是面向跨会话的持久化记录。

## 工作流程

### 1. 信息收集

从当前对话上下文中提取：

| 维度 | 说明 |
|------|------|
| 问题描述 | 用户原始输入、复现步骤、现象表现 |
| 调研路径 | 分析过程中查看了哪些文件、调用了哪些工具、排查了哪些方向 |
| 关键发现 | 根因分析、代码位置、配置差异、版本问题 |
| 涉及的代码/文件 | 需要列出完整的文件路径和关键代码片段 |
| 用户偏好 | 用户对方案是否有倾向性、是否有特殊约束 |

### 2. 内容组织

生成 Markdown 文档，必须包含以下章节：

```markdown
## 待处理 — {简短主题描述}（{YYYY-MM-DD}）

## 问题背景

{详细描述问题的发现过程、用户原始输入、现象表现、影响范围}
{引用用户原始描述和对话中的关键信息}
{如果在调研过程中发现了问题的根因，在此处详细记录发现过程}

## 分析结果

{全链路分析过程}
{根因定位，附带代码路径和关键代码片段}
{原因分析，解释为什么会发生此问题}
{影响评估}

## 建议的处理方式

{方案一：描述 + 步骤 + 预期效果}
{方案二（如有）：描述 + 步骤 + 预期效果}
{推荐方案及理由}

## 需要注意的点

{风险点 1 — 需要注意的边界情况}
{风险点 2 — 可能影响的关联模块}
{依赖项 — 需要其他团队/人员配合的事项}
{验证方式 — 修复后如何验证}
```text

### 3. 文件命名与输出分类规则

根据问题的规模和性质，选择正确的输出位置与命名规范：

- **小问题处理**（例如：Bug 修复、语法错误修复、简单的 UI 调整、短期即可完成的待办事项）：
  - **输出位置**：`docs/00-7待办/01-当前待办/`
  - **命名格式**：`待处理-{简短主题}-{YYYY-MM-DD}.md`
  - **正确示例**：`待处理-documents页面流式报告生成失效-2026-05-30.md`
  
- **大问题、未来构建或复杂功能**（例如：大型架构重构、全新功能设计、涉及跨多模块的复杂特性、非即时阻断的体验升级方案）：
  - **构建方式**：**必须且唯一**调用 `to-prd` 技能来构建与生成对应的 PRD 文档。
  - **输出位置**：`docs/00-7待办/02-短期规划/`
  - **命名格式**：`PRD-{简短主题}.md`
  - **正确示例**：`PRD-案件工作台文件上传与联动更新机制.md`

**命名约束**：
- **主题**：中文，简明扼要，用连字符分隔关键词。禁止使用拼音、英文或下划线（例如禁止 `待处理-fix_bug.md`）。
- **日期**（仅适用于当前待办）：使用对话发生日期（ISO 8601 格式，如 `YYYY-MM-DD`）。

### 4. 输出确认与位置创建

在新建文档前，确认目标位置目录是否存在，若不存在需先创建。

### 5. 写后确认

文件写入成功后，告知用户文件路径，并请用户确认内容是否完整、是否需要补充。

## 输入参数说明

| 参数名 | 类型 | 默认值 | 描述 |
| :--- | :--- | :--- | :--- |
| `title` | `string` | 自动生成 | 待办事项的简短主题，用于文件名和标题。留空则从对话中自动提取 |
| `date` | `string` | 当天日期 | 待办日期，格式 YYYY-MM-DD |
| `categories` | `array` | `[]` | 额外需要关注的维度，如 `["安全", "性能", "兼容性"]` |

## 输出示例

以下为小问题处理在 `docs/00-7待办/01-当前待办/` 下生成的当前待办文档示例（大问题/复杂功能参考此结构转换为标准的 PRD 输出到 `docs/00-7待办/02-短期规划/` 目录）：

```markdown
## 待处理 — 管理后台工作流校验误报 conditional 执行器（2026-05-30）

## 问题背景

用户反馈在管理后台的工作流协议校验页面中，对 `legal_analysis_default` 协议执行校验时，
返回了 2 个 fatal 级错误：节点 `triage_dispatcher` 和 `review_gate` 的执行器类型
`conditional` "未注册或非法"。

> 用户原始描述：「校验结果显示 conditional 执行器未注册，但这是协议层的路由控制原语，
> 不是业务执行器，校验器不应该对此报错。」

## 分析结果

### 根因定位

校验器 `protocol_validator.py` 的 `_validate_executor_registered` 方法仅检查
`NODE_REGISTRY`，而 `conditional` 是 LangGraph 的路由控制原语，并非业务执行器，
因此不在 `NODE_REGISTRY` 中。

在 `interpreter.py` 第 229 行有专门的处理代码：
```python
if node_def.executor == "conditional" and node_def.conditions:
    workflow.add_conditional_edges(...)
```text

但校验器未感知此逻辑，导致误报。

### 影响范围

- 仅影响校验结果展示，不影响运行时行为
- 所有使用 `conditional` 路由的协议均会触发此误报

## 建议的处理方式

### 方案：新增系统执行器白名单

**步骤**：

1. 在 `protocol_validator.py` 顶部定义：
   ```python
   SYSTEM_EXECUTORS = {"conditional"}
   ```text

1. 在 `_validate_executor_registered` 方法中，校验前先检查：
   ```python
   if executor in SYSTEM_EXECUTORS:
       return True
   ```

**预期效果**：校验通过，不再误报。

## 需要注意的点

1. **可扩展性**：如果未来新增 `parallel`、`subgraph` 等系统级执行器，也需加入白名单。
1. **数据库同步**：`workflow_protocol.json` 如有修改需同步到 `WorkflowConfig` 表。
1. **前端校验页面**：修复后需重新执行校验确认结果。

## 质量检查清单

在输出文档前，确认以下项目：

- [ ] 文件名与存放路径符合大小问题分类规范（小问题在 `01-当前待办` 使用 `待处理-{主题}-{日期}.md`；大问题/复杂功能在 `02-短期规划` 使用 `PRD-{主题}.md`）

## 核心约束与执行标准

### 严格边界与禁止项

- **安全 > 质量 > 速度**：任何全栈决策和代码修改必须遵循此总原则。
- **禁止项**：严禁在未经用户确认的情况下删除核心业务规则。

## 思维链引导

在执行复杂步骤、架构设计或遇到歧义时，必须通过 `<thought>` 标签显式输出你的思考过程和逻辑推导，然后再输出最终行动或代码方案。
