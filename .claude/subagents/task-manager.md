# task-manager

来源：`.agents/skills/` 合并组: task-recorder, task-handover, daily-progress-sync

## task-recorder

## 待办事项记录技能 (task-recorder)

## 何时使用

- 用户在对话中提出了一个需要后续跟进的问题或需求
- 经过调研和分析后，需要对问题和结论进行归档
- 用户明确要求"记录待办"、"归档这个问题"、"整理成待办"
- 对话中发现了值得记录的技术决策、架构隐患或待优化点

## 核心定位

该技能是知识沉淀工具，将对话中的隐性知识显性化，生成可直接用于项目管理的待办文档。不替代 TodoWrite 等实时任务跟踪工具，而是面向跨会话的持久化记录。

## 工作流程

### 1. 信息收集

从当前对话上下文中提取：

| 维度 | 说明 |
|------|------|
| 问题描述 | 用户原始输入、复现步骤、现象表现 |
| 调研路径 | 分析过程中查看了哪些文件、调用了哪些工具、排查了哪些方向 |
| 关键发现 | 根因分析、代码位置、配置差异、版本问题 |
| 涉及的代码/文件 | 需要列出完整的文件路径和关键代码片段 |
| 用户偏好 | 用户对方案是否有倾向性、是否有特殊约束 |

### 2. 内容组织

生成 Markdown 文档，必须包含以下章节：

```markdown
## 待处理 — {简短主题描述}（{YYYY-MM-DD}）

## 问题背景

{详细描述问题的发现过程、用户原始输入、现象表现、影响范围}
{引用用户原始描述和对话中的关键信息}
{如果在调研过程中发现了问题的根因，在此处详细记录发现过程}

## 分析结果

{全链路分析过程}
{根因定位，附带代码路径和关键代码片段}
{原因分析，解释为什么会发生此问题}
{影响评估}

## 建议的处理方式

{方案一：描述 + 步骤 + 预期效果}
{方案二（如有）：描述 + 步骤 + 预期效果}
{推荐方案及理由}

## 需要注意的点

{风险点 1 — 需要注意的边界情况}
{风险点 2 — 可能影响的关联模块}
{依赖项 — 需要其他团队/人员配合的事项}
{验证方式 — 修复后如何验证}
```text

### 3. 文件命名与输出分类规则

根据问题的规模和性质，选择正确的输出位置与命名规范：

- **小问题处理**（例如：Bug 修复、语法错误修复、简单的 UI 调整、短期即可完成的待办事项）：
  - **输出位置**：`docs/00-7待办/01-当前待办/`
  - **命名格式**：`待处理-{简短主题}-{YYYY-MM-DD}.md`
  - **正确示例**：`待处理-documents页面流式报告生成失效-2026-05-30.md`
  
- **大问题、未来构建或复杂功能**（例如：大型架构重构、全新功能设计、涉及跨多模块的复杂特性、非即时阻断的体验升级方案）：
  - **构建方式**：**必须且唯一**调用 `to-prd` 技能来构建与生成对应的 PRD 文档。
  - **输出位置**：`docs/00-7待办/02-短期规划/`
  - **命名格式**：`PRD-{简短主题}.md`
  - **正确示例**：`PRD-案件工作台文件上传与联动更新机制.md`

**命名约束**：
- **主题**：中文，简明扼要，用连字符分隔关键词。禁止使用拼音、英文或下划线（例如禁止 `待处理-fix_bug.md`）。
- **日期**（仅适用于当前待办）：使用对话发生日期（ISO 8601 格式，如 `YYYY-MM-DD`）。

### 4. 输出确认与位置创建

在新建文档前，确认目标位置目录是否存在，若不存在需先创建。

### 5. 写后确认

文件写入成功后，告知用户文件路径，并请用户确认内容是否完整、是否需要补充。

## 输入参数说明

| 参数名 | 类型 | 默认值 | 描述 |
| :--- | :--- | :--- | :--- |
| `title` | `string` | 自动生成 | 待办事项的简短主题，用于文件名和标题。留空则从对话中自动提取 |
| `date` | `string` | 当天日期 | 待办日期，格式 YYYY-MM-DD |
| `categories` | `array` | `[]` | 额外需要关注的维度，如 `["安全", "性能", "兼容性"]` |

## 输出示例

以下为小问题处理在 `docs/00-7待办/01-当前待办/` 下生成的当前待办文档示例（大问题/复杂功能参考此结构转换为标准的 PRD 输出到 `docs/00-7待办/02-短期规划/` 目录）：

```markdown
## 待处理 — 管理后台工作流校验误报 conditional 执行器（2026-05-30）

## 问题背景

用户反馈在管理后台的工作流协议校验页面中，对 `legal_analysis_default` 协议执行校验时，
返回了 2 个 fatal 级错误：节点 `triage_dispatcher` 和 `review_gate` 的执行器类型
`conditional` "未注册或非法"。

> 用户原始描述：「校验结果显示 conditional 执行器未注册，但这是协议层的路由控制原语，
> 不是业务执行器，校验器不应该对此报错。」

## 分析结果

### 根因定位

校验器 `protocol_validator.py` 的 `_validate_executor_registered` 方法仅检查
`NODE_REGISTRY`，而 `conditional` 是 LangGraph 的路由控制原语，并非业务执行器，
因此不在 `NODE_REGISTRY` 中。

在 `interpreter.py` 第 229 行有专门的处理代码：
```python
if node_def.executor == "conditional" and node_def.conditions:
    workflow.add_conditional_edges(...)
```text

但校验器未感知此逻辑，导致误报。

### 影响范围

- 仅影响校验结果展示，不影响运行时行为
- 所有使用 `conditional` 路由的协议均会触发此误报

## 建议的处理方式

### 方案：新增系统执行器白名单

**步骤**：

1. 在 `protocol_validator.py` 顶部定义：
   ```python
   SYSTEM_EXECUTORS = {"conditional"}
   ```text

1. 在 `_validate_executor_registered` 方法中，校验前先检查：

   ```python
   if executor in SYSTEM_EXECUTORS:
       return True
   ```

**预期效果**：校验通过，不再误报。

## 需要注意的点

1. **可扩展性**：如果未来新增 `parallel`、`subgraph` 等系统级执行器，也需加入白名单。
1. **数据库同步**：`workflow_protocol.json` 如有修改需同步到 `WorkflowConfig` 表。
1. **前端校验页面**：修复后需重新执行校验确认结果。

```text

## 质量检查清单

在输出文档前，确认以下项目：

- [ ] 文件名与存放路径符合大小问题分类规范（小问题在 `01-当前待办` 使用 `待处理-{主题}-{日期}.md`；大问题/复杂功能在 `02-短期规划` 使用 `PRD-{主题}.md`）
- [ ] 包含"问题背景"章节，清晰描述了问题发现过程
- [ ] 包含"分析结果"章节，定位了根因并提供了代码路径
- [ ] 包含"建议的处理方式"章节，给出了可操作的方案和步骤
- [ ] 包含"需要注意的点"章节，提示了风险和依赖
- [ ] 所有文件路径使用相对于项目根目录的路径
- [ ] 所有代码片段使用正确的语言标记
- [ ] 文档内容可以使用中文自然书写，禁止中英混杂的标题

## 核心约束与执行标准

### 严格边界与禁止项

- **安全 > 质量 > 速度**：任何全栈决策和代码修改必须遵循此总原则。
- **禁止项**：严禁在未经用户确认的情况下删除核心业务规则。

## 思维链引导

在执行复杂步骤、架构设计或遇到歧义时，必须通过 `<thought>` 标签显式输出你的思考过程和逻辑推导，然后再输出最终行动或代码方案。

## task-handover

## 任务交接技能 (task-handover)

### 何时使用

- 用户要求"任务交接"、"交接一下"
- 用户要求"总结当前对话"、"总结本轮工作"
- 用户要求"整理待完成/待验证事项"
- 用户要求"暂存工作进度"
- 用户要求"把当前进度交接给下一个 Agent"
- 需要在对话结束时生成一份结构化工作记录

### 核心定位

跨会话知识传递工具。将当前对话中的工作目标、完成情况、修改文件、关键决策、待办事项、验证状态等信息整理为交接文档，让接手者快速理解上下文。

### 工作流程

### 第 1 步：梳理用户目标

从当前对话中提取用户最初和最新的目标，区分：

- 原始需求
- 中途新增需求
- 已取消或已变化的需求
- 当前最终目标

输出时避免只复述一句话，应说明目标的上下文和完成标准。

### 第 2 步：梳理已完成事项

结合当前对话和实际操作，列出已经完成的工作。

每条完成事项应尽量包含：

- 做了什么
- 涉及哪个模块或文件
- 解决了什么问题
- 是否已经验证

如果只是创建、修改文档，也要明确说明"未涉及业务代码"。

### 第 3 步：收集修改文件

如当前环境允许，应检查本轮改动文件，例如：

- 使用 `git status` 查看工作区变更；
- 使用 `git diff --stat` 查看变更范围；
- 必要时查看具体 diff，确认修改内容。

输出修改文件时建议按类型分组：

- 文档
- 前端
- 后端
- 测试
- 配置
- 数据库迁移

如果无法执行命令或没有 Git 信息，应说明原因，并基于对话中已知操作列出文件。

### 第 4 步：提炼关键实现与决策

记录下一位接手者需要知道的关键背景，包括：

- 为什么这么改
- 采用了什么方案
- 放弃了什么方案
- 重要约束
- 兼容性或依赖要求
- 与既有规则、规范、工作流的关系

不要写泛泛而谈的内容，应聚焦本轮实际决策。

### 第 5 步：列出待完成事项

根据对话中尚未完成的内容，列出明确待办。

每条待办建议包含：

- 待办内容
- 推荐处理位置
- 优先级：高 / 中 / 低
- 前置条件或阻塞点

如果没有明确待办，应写：

> 当前未发现明确待完成事项。

### 第 6 步：列出待验证事项

将尚未执行或尚未确认的验证动作列为 checklist。

示例：

- [ ] 运行单元测试
- [ ] 运行前端构建
- [ ] 检查页面交互
- [ ] 确认命令文件可被正确识别
- [ ] 确认 Markdown 格式符合团队规范

如果某些验证无法执行，应说明原因。

### 第 7 步：列出已验证事项

记录已经运行过的验证命令、检查动作和结果。

格式建议：

- `命令或动作`：结果

例如：

- `git status --short`：确认仅存在文档变更。
- `npm test`：未运行，本轮未涉及前端逻辑。

不要把未运行的验证写成已验证。

### 第 8 步：说明风险与注意事项

列出可能影响接手的风险：

- 文件是否为新建
- 是否依赖未确认的工具规范
- 是否缺少上下文
- 是否存在未提交变更
- 是否存在测试未覆盖
- 是否涉及敏感信息、环境变量、数据库迁移等

### 第 9 步：给出下一步建议

为下一位接手者提供可执行建议，按优先级排序。

建议应具体，例如：

1. 先确认命令文件是否被正确加载。
1. 再用一次真实"任务交接"触发词测试输出格式。
1. 如团队有命令 front matter 规范，补齐元信息。

## 保存策略

当用户要求"保存交接文档"但未指定路径时，优先询问保存位置。

如用户要求直接保存且没有指定路径，可建议以下默认策略：

- **优先合并**：在 `docs/00-7待办/01-当前待办/` 目录下寻找现存的、属于当前周或当前项目阶段的交接文档（例如 `任务交接-Week2.md` 或 `任务交接-阶段三.md`）。如果存在，则向其追加合并新的交接内容。
- **新建规范**：如果不存在相应的现有文档，则以周或阶段为单位创建新的交接文档。**禁止使用 `YYYY-MM-DD` 格式**，应使用如 `docs/00-7待办/01-当前待办/任务交接-[WeekX/阶段X].md` 格式。

保存后应告知：

- 保存路径
- 是否新建文件
- 是否覆盖文件
- 是否还有待验证事项

## 输出要求

- 使用中文。
- 内容必须基于当前对话和实际操作，不要编造未发生的验证或改动。
- 如果信息不足，应明确写"当前对话未提供"或"尚未验证"。
- 待办和待验证事项优先使用 checklist。
- 修改文件路径应使用项目相对路径。
- 如果用户要求写入文件，写入前先确认目标路径是否存在；不存在时创建必要目录。
- 如果本轮有代码改动，交接内容必须包含测试/构建/格式化是否运行。
- 如果本轮只改文档，需明确"未涉及业务代码和测试执行"。

## 语言精简要求（硬性）

输出时遵循以下规则：

- **不要长篇大论**。每个条目控制在 1-3 句，直接陈述事实。
- **讲清楚"在做什么、做了什么、当前状态"** 即可，不要铺垫背景或解释原因（除非原因本身是交接关键信息）。
- **已完成事项**只陈述做了什么事、涉及什么文件、解决了什么问题。不要用"我完成了XXX"句式，除非该条目属于"已完成"章节且确实已完结。
- **待完成事项**直接写待办内容和优先级，不要加情绪词或模糊表述。
- **关键决策**一条一行，不展开讨论过程。
- 接手者要的是事实，不是汇报。

## 禁止事项

- 不要把该工作流文件本身当作交接结果长期覆盖，除非用户明确要求更新。
- 不要声称已运行未实际运行的命令。
- 不要省略失败、阻塞或未验证事项。
- 不要记录密钥、令牌、密码、Cookie、生产环境敏感配置等信息。
- 不要在未获用户要求时自动提交 Git、推送或创建 PR。

### 核心约束与执行标准

### 严格边界与禁止项

- **安全 > 质量 > 速度**：任何全栈决策和代码修改必须遵循此总原则。
- **禁止项**：严禁在未经用户确认的情况下删除核心业务规则或文档。
### 思维链引导

在执行复杂步骤、架构设计或遇到歧义时，必须通过 `<thought>` 标签显式输出你的思考过程和逻辑推导，然后再输出最终行动或代码方案。

## daily-progress-sync

## 每日开发进度逆向生成 (Daily Progress Sync)

### 何时使用

- 每日/每周需要向项目管理或需求方同步真实的开发进度。
- 历史开发记录过于简略或丢失，需要从真实代码库还原工作量与业务影响。
- 自动化撰写或扩充项目版本发布日志。

## 执行步骤

### Step 1: 提取指定日期的代码变更明细

使用 Git 获取目标日期的 `git log --stat` 及 Commit Message 历史，必要时对关键 Commit 使用 `git show` 读取代码 Diff。

### Step 2: 代码与业务逻辑映射分析

分析涉及的文件路径、类名、变量名变更，执行：
1. 聚类与分类（后端架构、前端交互、UI设计、ASR 核心、数据库等）
1. 提炼功能点（将代码变更提炼为直白的功能点）
1. 推演实际业务影响（包含核心代码文件名，阐述对系统或用户的实际价值）

### Step 3: 格式化表格生成

将聚合后的分析结果转化为标准 Markdown 表格：
`| 类别 | 功能点 / 事项 | 详细描述 (业务价值与实现细节) | 状态 |`

### Step 4: 注入目标进度文档

定位到目标进度文档对应日期区域，插入或替换生成的表格内容（按时间倒序排列）。

## 核心规则

- **代码即事实**：所有功能点必须在 Git 变更记录中有物理文件依据。
- **表头锁定**：表格列名为系统保留常量，禁止精简或重命名。
- **技术商业融合**：体现技术的硬核（文件名/架构变更）与业务的温度（提效/防漏/风控）。

## 输入参数

| 参数名 | 类型 | 默认值 | 描述 |
| :--- | :--- | :--- | :--- |
| `target_date` | `string` | 今天 | 目标日期，格式 YYYY-MM-DD |
| `doc_path` | `string` | `沟通记录/开发进度-飞箭.md` | 目标进度文档路径 |

```json
{
  "status": "success",
  "message": "进度同步完成",
  "data": {
    "date": "2026-06-08",
    "entries": [],
    "inserted_at": "沟通记录/开发进度-飞箭.md"
  }
}
```text
