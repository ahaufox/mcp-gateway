# 任务完成与验收强制标准

## 1. 任务完成标准纪律

### 1.1 "已完成"的准入门槛
一个任务标记为"已完成"前，必须同时满足以下条件：

1. **验收标准全部满足**：任务原始方案中定义的验收标准必须逐条可验证通过。"大部分完成"或"核心流程通了"不等于完成。
1. **无关键 TODO 残留**：代码中若存在标注关键未完成逻辑的 TODO 注释（如"真实流转逻辑待实现""此处需对接真实 API"等），该任务不得标记为已完成。
1. **Mock/占位已标注**：任何仍在使用 mock、stub 或占位实现的功能，必须在待办清单中明确标注"Mock/暂未对接"，不得混入"已完成"条目。

### 1.2 禁止的行为
- **禁止**将"UI 壳子完成"等同于"功能完成"
- **禁止**将"前端调通了 stub"等同于"前后端联调完成"
- **禁止**将有 TODO 标记关键未完成逻辑的任务标为"已完成"
- **禁止**在验收标准含"真实""完整""闭环""上线"等字眼时，用 mock 实现通过验收

### 1.3 分档标记要求
对于无法一次性完成的任务，必须使用以下分级标记，不得笼统标"已完成"：

| 标记 | 含义 | 示例 |
|------|------|------|
| **UI 完成** | 界面可交互，数据为假 | `创建连接弹窗 - UI 完成（接口未对接）` |
| **联调完成** | 前端调通后端接口，数据真实 | `MCP服务列表展示 - 联调完成` |
| **闭环完成** | 全链路真实逻辑跑通，返回真实结果 | `代理转换执行 - 闭环完成` |

## 2. 验收标准逐条核实机制

### 2.1 验收标准编写规范
在编写实施方案时，验收标准必须满足 **SMART** 原则：
- **具体的**：不是"接口可用"，而是"GET /api/mcps 返回 200 + 符合 Schema 的 JSON"
- **可测量的**：不是"性能好"，而是"响应时间 < 200ms"
- **可达成的**：在当前阶段可实现
- **相关的**：与任务目标直接相关
- **有时限的**：关联具体交付时间

### 2.2 验收前自查清单
标记任务完成前，必须执行以下检查：

1. 重新阅读任务原始方案中的验收标准条目
1. 逐条在实际代码/运行环境中验证，而非仅凭记忆
1. 检查代码中是否存在阻碍性的 TODO/FIXME 注释
1. 检查是否所有 mock/占位实现已在待办中透明标注
1. 若任务涉及前后端联调，确认端到端链路已实际跑通

### 2.3 验收未通过的处置
- 验收未通过的任务，状态必须保持"进行中"或降级为"部分完成"
- 不得为了进度表美观而虚假标记完成

## 3. Mock 与存存根透明管理

### 3.1 Mock 必须标注
所有 mock 数据、stub 接口、占位组件必须在以下位置同时标注：

1. **代码层面**：在函数/组件头注释中标注 `@mock` 或 `@stub`，说明真实实现缺失的原因
1. **待办清单层面**：在待办清单中对应条目标注 `[Mock]` 前缀，说明未对接的内容

### 3.2 静默降级禁令
**严禁**在 API 调用失败时静默降级为假数据而不通知用户。

允许的做法：
- 抛出错误，由 React Query 的 `isError` 状态驱动 UI 展示错误提示（或前端组件显式报错）
- 在 UI 上明确显示"服务暂不可用"并引导用户重试

禁止的做法：
- `catch` 中仅 `console.warn` 后返回 mock 数据
- 用户无感知地看到假数据，以为系统正常工作

### 3.3 Mock 转正条件
Mock 实现转为真实实现的触发条件必须明确写在待办中，例如：
- "等待 POST /api/mcp/run 接口完整实现后，移除 getMockData 降级逻辑"

## 4. 前后端联调验收强制要求

### 4.1 联调完成标准
前后端联调任务标记完成前，必须满足：

1. **真实网络请求**：前端实际发出 HTTP 请求到后端，而非通过 mock 拦截器
1. **真实数据流**：后端返回的数据来自真实接口响应，而非硬编码返回
1. **错误处理完整**：前端正确处理了 4xx/5xx/网络超时等情况
1. **权限校验通过**：涉及鉴权的接口已正常接入身份认证（若有）

### 4.2 端到端验证
联调类任务必须有端到端验证证据，以下至少满足一项：
- 提供 Swagger/OpenAPI 调试调用截图或 curl 执行结果
- 提供浏览器 Network 面板截图显示真实请求/响应
- 提供 E2E 测试用例通过结果

## 5. 测试覆盖要求

测试规范（分层测试策略、测试真实性要求、验收测试）请参阅：
- **`testing-tdd-skills-standards.md`**：完整的测试规范，包括 TDD 工作流、覆盖率要求。

测试执行纪律：在进行任务实施时，**绝对禁止**频繁执行全量测试或大量无关测试。优先执行与当前代码变动直接相关的单一测试文件或具体的单个测试用例。全量测试应仅在任务最终完成准备提交前执行一次。

## 6. 状态跟踪纪律

### 6.1 事实来源原则
待办清单的状态变更必须有可验证的代码证据支持：
- 标记"已完成" → 提供验收证据（见 §4.2）
- 标记"进行中" → 提供当前进展描述和剩余工作
- 标记"暂缓" → 提供暂停原因和恢复条件

### 6.2 定期复核
待办清单每周至少复核一次，检查：
- 是否有标记已完成但实际存在关键未完成逻辑的任务
- Mock/占位状态的标注是否仍然准确
