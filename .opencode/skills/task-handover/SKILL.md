# 任务交接技能 (task-handover)

## 何时使用

- 用户要求"任务交接"、"交接一下"
- 用户要求"总结当前对话"、"总结本轮工作"
- 用户要求"整理待完成/待验证事项"
- 用户要求"暂存工作进度"
- 用户要求"把当前进度交接给下一个 Agent"
- 需要在对话结束时生成一份结构化工作记录

## 核心定位

跨会话知识传递工具。将当前对话中的工作目标、完成情况、修改文件、关键决策、待办事项、验证状态等信息整理为交接文档，让接手者快速理解上下文。

## 工作流程

### 第 1 步：梳理用户目标

从当前对话中提取用户最初和最新的目标，区分：

- 原始需求
- 中途新增需求
- 已取消或已变化的需求
- 当前最终目标

输出时避免只复述一句话，应说明目标的上下文和完成标准。

### 第 2 步：梳理已完成事项

结合当前对话和实际操作，列出已经完成的工作。

每条完成事项应尽量包含：

- 做了什么
- 涉及哪个模块或文件
- 解决了什么问题
- 是否已经验证

如果只是创建、修改文档，也要明确说明"未涉及业务代码"。

### 第 3 步：收集修改文件

如当前环境允许，应检查本轮改动文件，例如：

- 使用 `git status` 查看工作区变更；
- 使用 `git diff --stat` 查看变更范围；
- 必要时查看具体 diff，确认修改内容。

输出修改文件时建议按类型分组：

- 文档
- 前端
- 后端
- 测试
- 配置
- 数据库迁移

如果无法执行命令或没有 Git 信息，应说明原因，并基于对话中已知操作列出文件。

### 第 4 步：提炼关键实现与决策

记录下一位接手者需要知道的关键背景，包括：

- 为什么这么改
- 采用了什么方案
- 放弃了什么方案
- 重要约束
- 兼容性或依赖要求
- 与既有规则、规范、工作流的关系

不要写泛泛而谈的内容，应聚焦本轮实际决策。

### 第 5 步：列出待完成事项

根据对话中尚未完成的内容，列出明确待办。

每条待办建议包含：

- 待办内容
- 推荐处理位置
- 优先级：高 / 中 / 低
- 前置条件或阻塞点

如果没有明确待办，应写：

> 当前未发现明确待完成事项。

### 第 6 步：列出待验证事项

将尚未执行或尚未确认的验证动作列为 checklist。

示例：

- [ ] 运行单元测试
- [ ] 运行前端构建
- [ ] 检查页面交互
- [ ] 确认命令文件可被正确识别
- [ ] 确认 Markdown 格式符合团队规范

如果某些验证无法执行，应说明原因。

### 第 7 步：列出已验证事项

记录已经运行过的验证命令、检查动作和结果。

格式建议：

- `命令或动作`：结果

例如：

- `git status --short`：确认仅存在文档变更。
- `npm test`：未运行，本轮未涉及前端逻辑。

不要把未运行的验证写成已验证。

### 第 8 步：说明风险与注意事项

列出可能影响接手的风险：

- 文件是否为新建
- 是否依赖未确认的工具规范
- 是否缺少上下文
- 是否存在未提交变更
- 是否存在测试未覆盖
- 是否涉及敏感信息、环境变量、数据库迁移等

### 第 9 步：给出下一步建议

为下一位接手者提供可执行建议，按优先级排序。

建议应具体，例如：

1. 先确认命令文件是否被正确加载。
1. 再用一次真实"任务交接"触发词测试输出格式。
1. 如团队有命令 front matter 规范，补齐元信息。

## 输出格式

默认使用以下 Markdown 结构：

```markdown
## 任务交接

## 1. 当前目标

-

## 2. 已完成事项

-

## 3. 修改文件清单

### 文档
-

### 前端
-

### 后端
-

### 测试
-

### 配置 / 其他
-

## 4. 关键实现与决策
-

## 5. 待完成事项
- [ ]

## 6. 待验证事项
- [ ]

## 7. 已验证事项
-

## 8. 风险与注意事项
-

## 9. 下一步建议
1.
```text

## 保存策略

当用户要求"保存交接文档"但未指定路径时，优先询问保存位置。

如用户要求直接保存且没有指定路径，可建议以下默认策略：

- **优先合并**：在 `docs/00-7待办/01-当前待办/` 目录下寻找现存的、属于当前周或当前项目阶段的交接文档（例如 `任务交接-Week2.md` 或 `任务交接-阶段三.md`）。如果存在，则向其追加合并新的交接内容。
- **新建规范**：如果不存在相应的现有文档，则以周或阶段为单位创建新的交接文档。**禁止使用 `YYYY-MM-DD` 格式**，应使用如 `docs/00-7待办/01-当前待办/任务交接-[WeekX/阶段X].md` 格式。

保存后应告知：

- 保存路径
- 是否新建文件
- 是否覆盖文件
- 是否还有待验证事项

## 输出要求

- 使用中文。
- 内容必须基于当前对话和实际操作，不要编造未发生的验证或改动。
- 如果信息不足，应明确写"当前对话未提供"或"尚未验证"。
- 待办和待验证事项优先使用 checklist。
- 修改文件路径应使用项目相对路径。
- 如果用户要求写入文件，写入前先确认目标路径是否存在；不存在时创建必要目录。
- 如果本轮有代码改动，交接内容必须包含测试/构建/格式化是否运行。
- 如果本轮只改文档，需明确"未涉及业务代码和测试执行"。

## 语言精简要求（硬性）

输出时遵循以下规则：

- **不要长篇大论**。每个条目控制在 1-3 句，直接陈述事实。
- **讲清楚"在做什么、做了什么、当前状态"** 即可，不要铺垫背景或解释原因（除非原因本身是交接关键信息）。
- **已完成事项**只陈述做了什么事、涉及什么文件、解决了什么问题。不要用"我完成了XXX"句式，除非该条目属于"已完成"章节且确实已完结。
- **待完成事项**直接写待办内容和优先级，不要加情绪词或模糊表述。
- **关键决策**一条一行，不展开讨论过程。
- 接手者要的是事实，不是汇报。

## 禁止事项

- 不要把该工作流文件本身当作交接结果长期覆盖，除非用户明确要求更新。
- 不要声称已运行未实际运行的命令。
- 不要省略失败、阻塞或未验证事项。
- 不要记录密钥、令牌、密码、Cookie、生产环境敏感配置等信息。
- 不要在未获用户要求时自动提交 Git、推送或创建 PR。

## 核心约束与执行标准

### 严格边界与禁止项

- **安全 > 质量 > 速度**：任何全栈决策和代码修改必须遵循此总原则。
- **禁止项**：严禁在未经用户确认的情况下删除核心业务规则或文档。
## 思维链引导

在执行复杂步骤、架构设计或遇到歧义时，必须通过 `<thought>` 标签显式输出你的思考过程和逻辑推导，然后再输出最终行动或代码方案。
